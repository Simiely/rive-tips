# 画板体检与交付整理

**TL;DR**：动效文件常常是**给设计师看的说明书**，不是**给运行时吃的交付件**。两者差距不在画面，在结构：命名、驱动模型、尺寸一致性、废弃残留。体检的价值是**在交给开发之前**把这些挑出来。

> 更新时间：2026-10-26 ｜ 方法已验证：33 个画板 / 92 个动画 / 280 个状态的实盘审计

## 一、为什么要体检

一个典型的中大型动效文件（几十个画板、上百个动画）会有这些问题，而且**画面看起来都正常**：

- 交互画板没有可驱动入口 → 上机后发现"动不了"
- 两个画板名字只差一个空格 → 代码按名字取，随机命中
- 同一个动效存在两份实现 → 改一处漏一处
- 规范说明板和产品画板混在一个文件里 → 导出的 `.riv` 带着一堆用不上的东西上机

这些问题靠看是看不出来的，得按结构读。

## 二、指纹：一个画板的结构画像

用 8 个数字概括一个画板：

```
状态机数 / 层数 / 状态数 / 动画状态数 / 转换数 / inputs 数 / listeners 数 / 线性动画数
```

足够区分"结构一样"和"看起来一样"。用途有三个：搬运后核验、改造前后对比、批量筛查异常。

读取方式见 [MCP 接入与联调](mcp.md) 的 `animation_editor`：

```
listStateMachines   → 状态机 id / 名字 / 层
queryStateMachine   → 展开某一台：layer / state / transition / condition / input / listener
listLinearAnimations→ 动画 id / 名字 / 时长
```

注意：这几个命令**只作用于活动画板**，要逐个 `focusArtboard`。

## 三、六类高频问题

### 1. 驱动模型混用（最致命）

Rive 有两套驱动方式：

| 模型 | 入口 | 代码侧怎么用 |
|---|---|---|
| State Machine Input（旧） | `inputs` + `listeners` + 转换条件 | 按名字取 input，`fire()` / 设布尔 / 设数字 |
| ViewModel（新） | `viewModel` 属性 + 数据绑定 | 取 ViewModel 实例，设属性；trigger 类型可 `fire()` |

实盘审计里常见的是**两种混着用**：十几个画板走 Input，几个画板走 ViewModel，代码侧得写两套适配。

更糟的是第三种：**两者都没有**。判据很简单——

> `inputs == 0` 且 `animCount ≥ 2` 且 `dataBinds == 0`

这种画板在编辑器里手点能播（状态机内部靠 exit time 自动流转），但**从代码无法触发指定分支**。看起来最"完整"的交互画板，恰恰可能是驱动不了的。

### 2. 命名撞车

| 形态 | 例子 | 后果 |
|---|---|---|
| 尾随空格 | `button` 与 `button␣` | 去掉空格后同名；代码按名字取 → 命中不确定 |
| 同一画板内动画重名 | 两个都叫 `down5` | `play("down5")` 结果不可预期 |
| 空格差异的孪生动画 | `up5` 与 `up5␣` | 同上 |
| 默认名残留 | `State Machine 1`、`Timeline 1/2/3` | 按语义名查找全部失效 |
| 序号后缀堆积 | `refresh-2`、`refresh-2 2` | 分不清哪个是当前版本 |

默认名是最普遍的：几十个画板里 `State Machine 1` 可以出现二十多次。**它不是错误，但对"按名字驱动"的运行时是致命的**。

### 3. 尺寸不一致

同一批画板里混着 `1920×1080` 和 `1920×1079`——差 1px。比例上用 `fit: contain` 缩放到目标屏会产生亚像素偏移，多画板拼接时能看出来。

交付前统一到目标屏幕分辨率，是成本最低的一步。

### 4. 双份实现（没用 Component）

同一个控件的动效在多个画板里各写一遍（按钮三份、浮层两份……）。改一处必漏一处。

Rive 有 Component + Library：同一个部件定义一次，多处实例化，改源全变。做交付整理时值得评估，但改造成本不低，属于第二阶段。

### 5. 空壳与残留

- 只有背景填充、没有内容的默认画板
- 名字带序号、实际零状态机零动画的重复拷贝
- 状态机里只有 Entry、**0 个转换**的"定义板"

这些在导出时都是纯负担，也污染按名字查找。

### 6. 规范板混在产品文件里

`xxx animation doc`、`整个系统动效描述` 这类**说明性画板**和功能性画板在同一个文件里。`.riv` 是整包导出的，运行时会连带加载所有画板。

交付件的做法：**只保留功能性画板**，规范单独放一个文件。

## 四、整理顺序（按风险排）

1. **先补驱动入口**——给"无入口"的交互画板加 ViewModel 触发或 Input，并跑一遍 `simulateStateMachine` 确认真的会跳
2. **再统一命名**——去尾随空格、消重、把 `State Machine 1` 改成语义名（`按钮按下`、`浮层展开`）
3. **再拆文件**——产品画板与规范板分离
4. **最后谈 Component 复用**——成本最高，收益看后续迭代频率

理由：1 决定"能不能上机"，2 决定"上机后能不能维护"，3 是体积与清洁度，4 是长期成本。

## 五、改造后怎么证明没改坏

用指纹做前后对比：

```
改造前采集 → 改名/删画板 → 改造后采集 → 逐画板比 8 项
```

改名不改变结构，指纹必须**完全一致**；删画板只应该影响总数。任何一项变了，说明动到了不该动的东西。

视觉确认用 `capture_artboard`，改名前后各截一张对比像素。
